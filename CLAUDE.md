# bank-ai-agent

Агент для проверки ковенантов корпоративных кредитов (Halyk AI Challenge). Полное
описание задачи и архитектура — см. [PLAN.md](PLAN.md). Кратко: один Python-агент
читает леджер транзакций + папку «грязных» PDF, определяет статус/значение/
транзакцию-доказательство для каждого ковенанта каждого заёмщика и собирает
`submission.json`. LLM-провайдер заменяем (по умолчанию — бесплатная модель,
Gemini 2.5 Flash), детерминированная логика (связка счёт↔сценарий, арифметика,
выбор транзакции-доказательства) — на чистом коде, без LLM.

## Git: автокоммит и автопуш после изменений

После каждого изменения файлов кода или структуры проекта (новый/изменённый/
удалённый файл в `src/`, `config/`, `tests/`, `pyproject.toml` и т.п.) сразу
создавай git-коммит и пушь его в `origin` — без отдельного запроса на каждый
коммит/пуш.

Правила:

- Коммить только релевантные изменённые файлы (`git add <конкретные файлы>`),
  никогда не `git add -A`/`git add .` вслепую — проверяй `git status` перед
  добавлением, чтобы случайно не закоммитить секреты (`.env`, ключи API) или
  сгенерированные артефакты.
- Не коммить содержимое `artifacts/` (результаты прогонов) — держи в `.gitignore`.
- Коммит-сообщение — короткое, по делу, на русском или английском, в духе
  Conventional Commits (`feat:`, `fix:`, `refactor:`, `chore:` и т.п.), отражает
  **зачем** сделано изменение, а не пересказ диффа.
- Всегда создавай новый коммит, никогда не используй `--amend` и не переписывай
  историю без явной просьбы пользователя.
- После коммита сразу `git push` в текущую отслеживаемую ветку (`origin`,
  обычно `main`) — обычный fast-forward push, без `--force`/`--force-with-lease`
  и без изменения истории.
- Force-push, работа с чужими ветками, удаление веток на удалённом репозитории —
  по-прежнему только с явным подтверждением в чате. Если обычный `git push`
  отклонён (например, remote ушёл вперёд) — не форсировать самостоятельно:
  остановиться и сообщить пользователю.
- Создание/закрытие PR, issues и любые другие действия с GitHub, кроме простого
  push коммитов в свою ветку, — по-прежнему требуют явного подтверждения.
- Если в рамках одного ответа сделано несколько логически независимых
  изменений — разбивай на несколько коммитов (каждый со своим push), а не один
  общий.

## .gitignore: держать в актуальном состоянии

`.gitignore` в корне репозитория должен всегда покрывать всё, что не нужно в
истории: `__pycache__/`, виртуальные окружения (`.venv/`), кэши тестов/линта
(`.pytest_cache/`, `.ruff_cache/`, `.mypy_cache/`), артефакты прогонов
(`artifacts/*`), секреты (`.env`, `.env.*`), IDE-файлы (`.vscode/`, `.idea/`),
ОС-мусор (`Thumbs.db`, `.DS_Store`) и любые другие временные/сгенерированные
файлы.

- Секреты (`.env` и любые файлы с API-ключами/токенами) — **никогда** не
  коммитятся, только шаблон `.env.example` с пустыми значениями.
- Перед `git add` всегда проверяй `git status`: если появился новый тип
  файла, которого не должно быть в репозитории (кэш, локальный конфиг IDE,
  сгенерированный артефакт) — сначала добавь для него правило в `.gitignore`
  отдельным коммитом, а не игнорируй разово через `git add <конкретные файлы>`.
- Если в рабочей копии уже лежат файлы, которые надо было игнорировать с
  самого начала, но они не попали в git (ещё не закоммичены) — не коммитить их,
  а добавить правило в `.gitignore`.
