# Архитектура: агент проверки ковенантов (Halyk AI Challenge)

## Контекст

Задача (`agentic-bank-public/CASE.ru.md`): по «грязному» набору данных — единому
леджеру транзакций (`master_ledger_2025.csv`, ~1470 строк, из них только 12 заёмщиков
целевые: P1–P10, B1, B4, остальные ~300 счетов в диапазоне ACC-9xxx — шум) и папке
из ~200 PDF с непрозрачными именами — определить для каждого заёмщика и каждого
пункта ковенанта (6.1/6.2/6.3) статус (`COMPLIANT`/`BREACH`), фактическое значение
(`actual`) и, если применимо, транзакцию-доказательство (`evidence_txn_id`), и
выгрузить это в `submission.json` строго по форме `submission_template.json`.

Разведка документов (агент прочитал ~25 PDF из разных диапазонов размеров) показала:

- **~60–70% документов — шум**: типовые политики, служебные записки, страховки,
  IT-инциденты, пресс-релизы — почти дословно повторяются между компаниями, без
  `account_id` и без отношения к ковенантам.
- **Кредитные договоры** («Статья 6 — Финансовые ковенанты») содержат три пункта:
  6.1 — ratio-тест (например, налоги+коммуналка / EBITDA), 6.2 — минимальная выручка
  (абсолютный порог в USD), 6.3 — максимум платежей связанным сторонам. Пороги
  отличаются между версиями договора одного заёмщика (текущая 2025 vs просроченная
  2024, помечена как «НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ»).
- **KYC-досье** содержат `account_id` и **порог связанности** (% владения) —
  индивидуальный на компанию — от которого зависит, кто считается related party
  для 6.3.
- **Аудиторские записки** содержат реклассификации конкретных транзакций
  (например, перенос суммы из «Consulting» в «Operating Expenses»), причём
  встречаются черновики vs финальные версии — использовать нужно только финальную.
- Валюты в леджере смешаны (минимум USD/EUR).

Это классическая связка «зашумлённый unstructured + structured источник → точный
структурированный ответ», и пользователь попросил спроектировать **не разовый
скрипт под этот кейс, а переиспользуемый фреймворк** на **Python**, с архитектурой,
которую легко расширять/менять/выпиливать по частям. Модель для LLM-вызовов —
**бесплатная** (например, Google Gemini 2.5 Flash через Google AI Studio free
tier — рекомендованный вариант: щедрая бесплатная квота и нативная работа с PDF);
провайдер и конкретная модель — заменяемый параметр конфига, а не хардкод, именно
для того чтобы можно было безболезненно сменить модель или провайдера в будущем.
Это **один агент** (единый пайплайн, один запуск → один `submission.json`),
внутри которого несколько LLM-вызовов с разными ролями (классификация,
извлечение по типу документа) — не мульти-агентная система.

Кодовая база `bank-ai-agent` сейчас пустая — это проектирование с нуля, без
существующих паттернов для сохранения.

## Рекомендуемый подход

### Принцип №1 — LLM только там, где нужно понимание текста

Всё, что можно посчитать детерминированным кодом (связка `account_id` ↔
`scenario_id` через префикс `txn_id`, выбор актуальной версии документа по дате,
арифметика по леджеру, проверка «какая транзакция определяет вердикт»), считается
кодом, а не LLM. LLM отвечает только за: классификацию документов,
извлечение структурированных фактов из текста (условия ковенанта, связанные
стороны, реклассификации). Это даёт детерминируемость и укладывается в жёсткий
5%-допуск на `actual` в оценке.

### Принцип №2 — Framework/Case разделение (ports & adapters)

`core/` — не знает ничего про Halyk, PDF-хеши или пункты 6.1–6.3. Все специфичные
для конкретного кейса вещи (промпты, формат шаблона ответа, конвенция
`scenario_id`) вынесены в `config/cases/<case_name>/`. Новый кейс в будущем — это
новый конфиг + промпты, а не переписывание ядра.

### Принцип №3 — Пайплайн из независимых, тестируемых стадий

Каждая стадия — чистая функция от входа к выходу, с промежуточным артефактом на
диске (JSON), который можно посмотреть глазами и на который можно написать unit-тест
без вызова LLM. Стадии не знают о существовании друг друга напрямую — только через
типизированные модели данных (Pydantic) и оркестратор.

### Принцип №4 — Стратегии проверки ковенантов через реестр, а не if/else

Типы ковенантов (ratio-тест, абсолютный потолок, минимальный порог, лимит на
связанные стороны) реализуются как отдельные классы с одним интерфейсом
(`CovenantStrategy.evaluate(...)`), выбираемые по полю `test_type`, которое
извлекает LLM из текста договора. Добавить новый тип ковенанта — добавить один
файл и одну строку в реестре, ничего не трогая в остальном пайплайне.

## Структура проекта

```
bank-ai-agent/
  pyproject.toml
  README.md
  config/
    cases/
      halyk_2025/
        case.yaml            # пути к данным, правило scenario_id, схема шаблона
      prompts/
        classify_document.md
        extract_loan_agreement.md
        extract_kyc_dossier.md
        extract_audit_note.md
  src/bank_ai_agent/
    core/                     # framework-уровень, кейс-агностичный
      models.py               # Transaction, Document, CovenantDefinition, CovenantResult, Scenario
      pipeline.py             # оркестратор стадий (ingest→extract→resolve→evaluate→assemble)
      cache.py                # кэш LLM-вызовов по хешу(документ + версия промпта)
      llm/
        client.py             # провайдер-агностичная обёртка (retry, structured output, логирование токенов)
        providers/              # адаптеры под конкретных провайдеров (gemini.py, anthropic.py, ...)
        schemas.py            # JSON-схемы для structured output
    ingestion/
      ledger_source.py        # CSV → List[Transaction]
      document_source.py      # папка → List[Document] (текст из PDF: pdfplumber/pymupdf)
      template_loader.py      # submission_template.json → AnswerGrid (что нужно заполнить)
    extraction/
      classifier.py           # дешёвый проход: тип документа + кандидат account_id/company
      extractors/
        base.py                # Protocol Extractor
        loan_agreement.py
        kyc_dossier.py
        audit_note.py
    resolution/
      account_scenario_linker.py   # ACC-xxxx → scenario_id по префиксу txn_id (чистый код)
      version_resolver.py          # текущая vs просроченная редакция документа
      ledger_adjuster.py           # применяет реклассификации, метит related-party
    evaluation/
      strategies/
        base.py                 # Protocol CovenantStrategy
        ratio_test.py
        absolute_cap_test.py
        minimum_floor_test.py
        related_party_cap_test.py
      evidence_selector.py       # «удалить транзакцию → вердикт меняется?» — детерминированно
      registry.py                # test_type → класс стратегии
    assembly/
      answer_writer.py           # заполняет submission.json по шаблону
      validator.py                # ключи 1-в-1 с шаблоном, типы, actual>0, 2 знака
    cli.py                        # `python -m bank_ai_agent run --case halyk_2025`
  artifacts/                      # результаты прогонов, в .gitignore
    <run_id>/
      classified_documents.json
      extracted_facts.json
      adjusted_ledger.json
      submission.json
      trace.jsonl
  tests/
    unit/                         # стратегии и резолверы — без сети, на фикстурах
    fixtures/
```

### Поток данных

1. **Ingestion** — леджер → `Transaction[]`; папка документов → `Document[]` (сырой
   текст + путь + хеш); шаблон ответа → список ячеек, которые нужно заполнить.
2. **Extraction** — `classifier.py` дешёвым промптом сортирует документы по типам и
   отсеивает шум; только релевантные документы идут в специализированные
   экстракторы, которые возвращают структурированные факты с указанием
   документа-источника (для трассируемости).
3. **Resolution** — линковка счёт↔сценарий (код), выбор актуальной версии договора
   и аудиторского заключения (код + сигналы из extraction), применение
   реклассификаций и меток related-party к транзакциям сценария → «скорректированный
   леджер» на сценарий.
4. **Evaluation** — для каждой (сценарий, пункт ковенанта) выбирается стратегия из
   реестра по `test_type`, считается `status`/`actual`; `evidence_selector`
   детерминированно проверяет, какая одна транзакция меняет вердикт при удалении.
5. **Assembly** — заполнение `submission.json`, строгая валидация против
   `submission_template.json` (никаких добавленных/переименованных/пропущенных
   ключей — иначе ячейка не засчитывается по правилам оценки).

### LLM-слой

- `llm/client.py` — провайдер-агностичный интерфейс (`Provider.extract(prompt,
  schema, document) -> dict`), конкретный провайдер и модель — параметр конфига,
  а не хардкод. Первый адаптер — `providers/gemini.py` (Google AI Studio free
  tier, модель по умолчанию `gemini-2.5-flash` — нативно читает PDF, щедрая
  бесплатная квота); при желании позже добавляется `providers/anthropic.py` без
  изменений в остальном пайплайне.
- Structured output через JSON Schema / function-calling на каждой границе LLM —
  никакого парсинга свободного текста.
- Промпты — версионируемые файлы в `config/prompts/`, не строки в коде.
- Кэш по хешу (документ, версия промпта) — при повторных прогонах не платим за
  неизменившиеся документы и не упираемся в лимиты бесплатной квоты.
- Двухпроходная схема (дешёвая классификация → дорогое извлечение только для
  релевантных ~30–40% документов) экономит вызовы и бесплатную квоту.

## Проверка результата

- В `agentic-bank-public/ground_truth.json` уже лежат эталонные ответы для всех 12
  сценариев (P1–P10, B1, B4) — использовать как **локальный offline-харнесс**:
  небольшой скрипт оценки, реализующий формулу из раздела 4 CASE.ru.md (0.5 за
  status, 0.3 по убывающей шкале за actual, 0.2 за evidence_txn_id), гоняется на
  каждом прогоне пайплайна и даёт числовую обратную связь до реальной отправки.
- Unit-тесты на `evaluation/strategies/*` и `resolution/*` на синтетических
  фикстурах (без сети) — это код, а не LLM, должен быть детерминированным и
  тестируемым.
- `assembly/validator.py` — обязательный гейт перед записью `submission.json`:
  ключи совпадают 1-в-1 с `submission_template.json`, `status` ровно
  `COMPLIANT`/`BREACH`, `actual` — положительное число с 2 знаками.
- End-to-end: полный прогон `cli.py run --case halyk_2025` → `submission.json` →
  локальный скоринг против `ground_truth.json`.
